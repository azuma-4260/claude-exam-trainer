# grill-me

計画・決定・アイデアについて、**共通理解に到達するまでユーザーを問い詰める**。

対象を **design tree**(決定木)として捉える。ひとつの決定は、その下にぶら下がる
決定へ分岐する。

## 進め方

木を**ラウンド**単位で進める。**frontier** とは「前提となる決定がすでに確定していて、
まだ聞いていない答えを推測せずに *今* 聞ける質問」の集合。

1. frontier をすべて洗い出し、**1 ラウンドでまとめて聞く**。各質問に番号を振り、
   **自分の推奨案を必ず添える**
2. ユーザーの回答を待つ。回答が木を作り替える(確定した決定が frontier を外へ押し出し、
   それに依存していた質問が解放される)
3. frontier を再計算して次のラウンドへ

**同じラウンド内の未解決質問に答えが依存する質問は、そのラウンドではなく後のラウンドに属する。**

## ラウンドの書式

```
❓ **Q1** - **<質問タイトル>**: <質問本文。複数段落・選択肢の提示可>

➡️ <推奨案>

---

❓ **Q2** - **<質問タイトル>**: <質問本文>

➡️ <推奨案>
```

## 事実は自分で取りに行く

**事実 (facts) を集めるのは常に自分の仕事で、ユーザーの仕事ではない。**
frontier の質問が環境側の事実(ファイルシステム、既存実装、`specs/`、依存のバージョン、
外部ドキュメント等)を必要とするなら、自分で調べる。調べればわかることをユーザーに聞かない。

ただし**そこでブロックしない**。実行中の調査は「未確定の前提」なので、待つのは
その調査の下流にある質問だけ。frontier の残りは今すぐ聞く。

**決定 (decisions) はユーザーのもの。** ひとつずつ提示して回答を待つ。

## 終了条件

frontier が空になったとき。design tree の全ブランチを訪問し、黙って仮定したものが
何も残っていない状態。**ユーザーが「共通理解に到達した」と確認するまで、実装に着手しない。**

## このリポジトリでの注意

- 会話は日本語(`AGENTS.md` の規約)。ただし成果物の英語規約(問題文 stem は英語)は変えない
- 事実確認の前に `specs/` を読む。仕様とユーザーの発言が食い違ったら、それ自体を質問にする
  (spec が正、変えたいなら spec を先に更新する、というルールがあるため)
- README の「停止条件」に該当する論点(永続データの意味・スキーマ、状態遷移、採点、
  SRS スケジューリング、Mock の holdout / スコア、認証・認可境界、本番データの変更・破壊)は
  **必ず frontier に載せる**。ここを暗黙に決めてはいけない
- サブエージェントで事実調査する場合、`.claude/settings.json` の PreToolUse フックにより
  `model` の明示が必須(機械的作業 = haiku、標準ファンアウト = sonnet)
