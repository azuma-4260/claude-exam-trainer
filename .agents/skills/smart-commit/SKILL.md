# smart-commit スキル

変更されたファイルを分析し、関連する変更を論理的にグループ化して、適切なコミットメッセージで複数のコミットを自動作成します。

呼び出しは Claude Code が `/smart-commit`、Codex が `$smart-commit`。

**重要: このスキルの呼び出し自体がコミット実行の承認です。** コミット計画を提示したあとは、ユーザーへの確認を挟まずそのままコミットまで実行してください。ただし以下の場合のみ一時停止して確認します:
- 未追跡ファイルにバイナリ・一時ファイル(`.DS_Store` / `~$` 等)や生成物が含まれ、コミット対象に含めるか判断が必要な場合
- 機密情報・認証情報を含む可能性のあるファイル(`.env*`、`.vercel/project.json`、鍵・トークンらしき値)が検出された場合。**値は表示せずパスだけを報告する**

## 処理手順

### 1. 変更ファイルの確認と分析

まず、以下のコマンドを並列実行して現状を把握してください:
- `git status --porcelain --untracked-files=all` で変更されたファイルリストを取得
- `git diff --stat` で変更の統計情報を取得
- 各変更ファイルの `git diff` で具体的な変更内容を確認

### 2. 変更の自動分類

以下のカテゴリーに基づいて変更を分類してください:

#### **仕様系** (`spec`)
- ファイル: `specs/*.md`, `README.md`(設計書の正本)
- コミットタイプ: `docs:`(仕様の追記・改訂)/ `fix:`(仕様の誤り訂正)
- 注意: 仕様変更は実装より**先**に入る。実装と同じコミットにまとめてよいのは「spec を直してその場で追従実装した」場合のみ

#### **バンク / コンテンツ系** (`bank`)
- ファイル: `content/**`(`questions/*.json`, `syllabus.yaml`, `SOURCES.md`, 台帳類)
- コミットタイプ: `feat:`(問題・フラッシュ追加)/ `fix:`(問題文・正解・解説の誤り修正)/ `chore:`(監査記録・台帳更新)
- 注意: 問題の追加・改訂は `npm run validate-bank` が緑であること

#### **アプリ実装系** (`app`)
- ファイル: `src/**`(`app/`, `components/`, `lib/`, `db/` 等)
- コミットタイプ: `feat:`(新機能・新画面)/ `fix:`(バグ修正)/ `refactor:`(構造整理)
- 注意: 同居する `*.test.ts` は**実装と同じコミットに含める**(README 常時遵守 2 のテスト先行により、テストだけ先に分離すると main に red が入る)

#### **スクリプト / ツール系** (`scripts`)
- ファイル: `scripts/**`(`validate-bank`, `task/*`, `audit:*` 等)とその `*.test.ts`
- コミットタイプ: `feat:` / `fix:` / `chore:`

#### **DB / マイグレーション系** (`db`)
- ファイル: `drizzle/**`, `drizzle.config.ts`
- コミットタイプ: `feat:`(スキーマ追加)/ `chore:`(migration 生成・適用)
- 注意: migration は排他ロック対象(`specs/10` §3 `EXCLUSIVE_LOCKS`)。スキーマ定義(`src/db/`)と生成された migration は**同じコミット**にまとめる

#### **タスク運用系** (`ops`)
- ファイル: `tasks/status/*.yaml`(台帳), `tasks/backlog/*.md`(起票), `tasks/README.md`
- コミットタイプ: `chore:`
- 注意: 台帳の `state: merged` / `state: done` は `tasks/README.md`「完了の記録」の規約どおり**独立コミット**にする。実装と混ぜない

#### **エージェント設定系** (`agents`)
- ファイル: `.agents/**`(スキル正本), `.claude/**`(symlink・settings・フック), `AGENTS.md`, `CLAUDE.md`
- コミットタイプ: `feat:`(スキル新規追加)/ `chore:`(設定変更)/ `docs:`(指示ファイル更新)

#### **ビルド / CI 設定系** (`config`)
- ファイル: `package.json`, `package-lock.json`, `next.config.ts`, `tsconfig.json`, `eslint.config.mjs`, `vitest.config.ts`, `postcss.config.mjs`, `components.json`, `vercel.json`, `.github/workflows/**`, `.gitignore`
- コミットタイプ: `chore:`
- 注意: `package-lock.json` の変更は排他ロック対象。依存の無目的な更新は禁止(README 実装契約 5)なので、意図しない lock 差分が混ざっていたら**コミットせず報告する**

#### **その他** (`misc`)
- 上記に該当しないファイル

### 3. グループ化のルール

1. **同じカテゴリー内で関連性が高い変更**: 1つのコミットにまとめる
   - 例: `src/lib/queue.ts` と `src/lib/queue.test.ts` の「時間予算キューの実装」→ 1コミット
2. **異なるカテゴリーでも同じ目的の変更**: 1つのコミットにまとめる
   - 例: `src/db/schema.ts` と `drizzle/0003_*.sql` の「attempt テーブル追加」→ 1コミット
3. **独立した大きな変更**: 個別のコミットに分離
   - 例: 「模試レポート画面の実装」と「フラッシュ 30 枚追加」→ 2コミット
4. **仕様・台帳と実装**: 分離する
   - 例: `specs/04` の改訂 と `src/lib/srs.ts` の実装 → 2コミット(spec が先)
   - 例: `tasks/status/D1-2.yaml` の `state: done` と実装 → 2コミット(台帳は独立)

### 4. コミットメッセージの生成

```
<type>: <日本語の簡潔な要約>

<必要に応じて詳細説明>
```

#### Type の選択基準
- `feat:` - 新機能・新画面・新スキル・問題の新規追加
- `fix:` - バグ修正・仕様誤りの訂正・問題文/正解/解説の誤り修正
- `refactor:` - 振る舞いを変えない構造の整理
- `docs:` - 仕様書・指示ファイルのみの変更
- `chore:` - 設定・台帳・migration 生成・監査記録

#### メッセージの例
- `feat: 間違いノートと総ざらい学習を追加`
- `fix: holdout ゲートが未提出フォームの問題を Practice に漏らす不具合を修正`
- `docs: specs/04 に時間予算キューの打ち切り条件を追記`
- `chore: D1-2 を台帳に done 記録`

### 5. 未追跡ファイルの処理

`??`(untracked files)については、以下のように処理してください:

1. **コミットすべきファイル**(確認不要・そのままコミット対象に含める):
   - `specs/*.md`, `content/**`, `src/**`, `scripts/**`, `drizzle/**`
   - `tasks/backlog/*.md`, `tasks/status/*.yaml`
   - `.agents/skills/**`(スキル正本), `.claude/skills/*`(正本への symlink)
2. **除外を推奨するファイル**(コミット対象から除外し、含めるか確認する):
   - `.DS_Store` などのシステムファイル、`~$` で始まる一時ファイル
   - ビルド生成物・ログ・スクラッチ(`.next/`, `*.log`, 一時 JSON 等)
3. **絶対にコミットしない**(検出したらパスだけ報告して停止):
   - `.env*`, `.vercel/project.json`、その他の資格情報を含むファイル

### 6. コミット計画の提示

以下の形式で、コミット計画を提示してください。**提示後はそのまま手順7のコミット実行に進みます**(承認待ちはしません):

```markdown
## 📋 コミット計画

以下の変更を **N個のコミット** に分けて実行します:

### コミット 1: <type>: <要約>
**含まれるファイル:**
- `path/to/file1.ts` (+XX -YY行)

**変更内容:**
<簡単な説明>

---

### 未追跡ファイル (確認が必要なものがある場合のみ)
- `scratch.json` → 除外(非推奨: 一時ファイル)。含める場合は指示してください。
```

### 7. コミット実行

計画を提示したら、続けて以下の手順で実行してください:

1. 各コミットグループごとに `git add <ファイル...>` → `git commit -m "<メッセージ>"`
2. 各コミット後に `git log -1 --oneline` で結果を確認
3. すべてのコミットが完了したら、最終確認として `git status` を実行

## 注意事項

- 関連性のない変更を1つのコミットにまとめないでください
- コミットメッセージは変更の「何を」ではなく「なぜ/何のために」を重視してください
- 1コミット = 1つの論理的変更。大きな変更は分割してください
- Conventional Commit 形式を厳守し、メッセージは日本語で簡潔に
- **push・merge はしない**。このスキルの責務は commit まで(`/task-session` の承認境界を壊さないため)
- スキルの呼び出し自体が承認であるため、計画提示後は確認を挟まずコミットを実行してください(手順5・冒頭の例外を除く)
