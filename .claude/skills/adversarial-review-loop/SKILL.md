# adversarial-review-loop スキル

自分が作った成果物を自分で見直すと、どうしても「正しいはずだ」という確証バイアスがかかる。
このスキルは、成果物の作成に関与していない**独立したコンテキストのサブエージェント**に
「欠陥を見つけることが仕事、安易な承認は失敗」という敵対的な立場でレビューさせ、
Blocking 指摘がなくなるまで修正ループを回すことで、この問題を回避する。

**重要: このスキルの呼び出し自体がループ実行の承認です。** ラウンドごとにユーザーへ確認を
求めず、Pass または停止条件に達するまで自律的にループを回すこと。

サブエージェントの起動には、この環境でサブエージェント委譲に使うツール(環境・バージョンに
より `Agent` または `Task` という名前)を使う。**どちらも使えない場合はこのスキルの根幹が
成立しないため、自分でレビューを代替せず、その旨をユーザーに報告して中止する。**

## 用語

| 用語 | 意味 |
|---|---|
| ラウンド | 「レビュアー起動 → 指摘の検証 → 修正」の 1 サイクル |
| P1 (Blocking) | 仕様違反・データ破壊・誤動作・セキュリティ欠陥など、このままでは出せない指摘 |
| P2 (Major) | 動くが将来の欠陥や保守困難を生む問題。原則修正する |
| P3 (Minor) | 好み・軽微な改善。記録するが修正は任意 |
| 棄却 | 検証の結果、指摘が事実誤認・仕様の誤読だと確認されたもの(修正しない) |
| 許容 | 指摘は事実だが、仕様上許される意図的な設計判断として修正しないもの(P1 は許容不可) |
| Pass | あるラウンドのレビューで、新規の P1・P2 指摘が 1 件も出なかった状態(下記「Pass 判定」参照) |

## 処理手順

### 1. レビュー対象と Pass 基準の確定

ループを始める前に、以下を明確にして最初に 1 度だけ提示する:

1. **対象**: 直前の作業成果物。通常は未コミット差分と新規作成ファイル
   (`git status` / `git diff` で確認。**新規 = untracked ファイルは `git diff` に現れない**ので、
   `git status` で列挙してファイル自体を対象に含める)。
   ユーザーが対象を指定した場合(特定ファイル・ブランチ差分 `--base main` 等)はそれに従う。
   対象が曖昧なら、直前の会話で作成・変更したファイル群を対象とみなす。
   **対象を確定できない場合(差分も新規ファイルもない・指定されたファイルが存在しない等)は、
   推測で対象を広げてループを始めず、ユーザーに対象を確認する。**
2. **観点**: 成果物の種類に応じてレビュー観点を決める(手順 2 のレンズ参照)。
3. **Pass 基準**: 手順 5 の「Pass 判定」を既定とする。
4. **関連仕様**: このリポジトリでは `specs/` が唯一の仕様ソース。対象に関係する spec と
   `AGENTS.md` の禁止事項を特定し、レビュアーへの指示に含める(リポジトリ外の成果物なら
   ユーザー要求・会話中の要件が仕様に相当する)。
5. **開始時スナップショット**: ループ中の修正は未コミットの作業ツリーを直接上書きするため、
   誤った修正をした場合に開始時点へ戻れるよう、開始前に状態を退避する
   (例: `git stash create` の結果を控える、対象の差分とファイルをスクラッチ領域へコピーする)。
   退避先は最終報告まで保持する。

### 2. 敵対的レビューラウンドの実行

サブエージェントとしてレビュアーを起動する。**毎ラウンド新規に起動し、前ラウンドの
レビュー結果は渡さない**(前任者の結論に引きずられるのを防ぐ。修正済みの成果物そのものだけを
見せる)。

- 既定は **2 体を並列起動**し、異なるレンズを割り当てる。成果物が小さい(数十行以下)なら
  1 体でよいが、その場合は **1 体にレンズ A・B の両方を兼務させる**(観点の欠落を作らない)。逆にサブエージェント 1 体のコンテキストに収まらない規模なら、対象をファイル・
  機能単位に分割してレビュアーを増やし、**各自の担当範囲を明示して全域をカバーする**
  (担当範囲外を読んだ気にさせない。網羅性はレビュアーの自己申告に頼らず本体が担保する)。
  - レンズ A: **仕様適合・正確性**(spec との突き合わせ、ロジックの誤り、採点・状態遷移・
    データの意味の逸脱)
  - レンズ B: **堅牢性・エッジケース**(境界値、異常系、並行性、冪等性、セキュリティ、
    禁止事項への抵触)
  - ドキュメントやスキル定義が対象の場合は「矛盾・曖昧さ・実行不能な指示」
    「読者が誤解するケース」に読み替える。
- レビュアーへのプロンプトには以下を必ず含める(severity 定義を渡さないとレビュアーの基準が
  本体のトリアージ基準とずれるので、定義の同梱は省略しない):

```
あなたは敵対的レビュアーです。以下の成果物の欠陥を見つけることが仕事であり、
欠陥を見逃して承認することが最大の失敗です。ただし存在しない欠陥の捏造も失敗です。
確信が持てない指摘は severity を下げるか「要確認」と明記してください。

あなたは読み取り専用です。レビュー対象を含む一切のファイルを変更・作成・削除しては
いけません。欠陥を見つけても自分で直さず、報告だけを返してください(修正の要否は
依頼元が判断します)。

## レビュー対象
<対象ファイル一覧。差分レビューなら diff の取得方法(例: git diff <range>)。
 新規ファイルは diff に出ないため、ファイルパスを列挙して直接読ませる>

## 前提資料(必ず読むこと)
<関連 spec のパス、AGENTS.md の禁止事項、ユーザー要求の要約>

## 担当レンズ
<レンズ A または B の内容。分割レビューなら担当範囲も明記>

## severity の基準
- P1 (Blocking): 仕様違反・データ破壊・誤動作・セキュリティ欠陥など、このままでは出せないもの
- P2 (Major): 動くが将来の欠陥や保守困難を生むもの
- P3 (Minor): 好み・軽微な改善

## 出力形式(最終メッセージにこの形式だけを返す)
指摘ごとに:
- severity: P1 / P2 / P3
- 場所: ファイルパス:行番号
- 内容: 何が問題か(1〜2 文)
- 失敗シナリオ: この欠陥が実害になる具体的な入力・状態・手順
- 根拠: spec の該当箇所、または論理的な理由

指摘が 1 件もない場合のみ、最終行に「PASS」とだけ書いてください。
指摘がある場合に PASS と書いてはいけません。
```

- 失敗シナリオを必須にしているのは、「なんとなく怪しい」だけの指摘を排除するため。
  シナリオを書けない指摘は検証段階で棄却しやすくなる。
- **レビュアーの出力が形式に従っていない場合**: 「PASS」の文字列だけで判定しない。
  指摘と PASS が併記されていたら PASS は無効で、指摘として扱う。散文で返ってきたら内容から
  指摘を抽出して検証にかける。出力が空・エラー終了・抽出不能なら、**そのレビュアーだけ**を
  同一指示で 1 回再起動する(同一ラウンド内の処理であり、ラウンド数は増えない。成立している
  他のレビュアーの指摘はそのまま保持して検証にかける)。再起動しても不成立なら、そのラウンドは
  不成立として 1 ラウンド消費し、次のラウンドとして作り直す。
- **ラウンド終了時の状態確認**: レビュアーが誤って成果物を変更していないか、起動前後で
  `git status` / 差分を突き合わせて確認する。変更されていたら開始時スナップショットから
  巻き戻し、そのレビュアーの指摘は報告部分のみ採用する。

### 3. 指摘の検証(トリアージ)

レビュアーの指摘を**鵜呑みにしない**。捏造・誤読された指摘に従って修正すると、正しいコードを
壊すことになる。全指摘について本体側でコードと spec を読み直し、以下に分類する。あわせて
severity の妥当性も見直す(軽微な好みが P1 になっていたら下げ、Blocking が P3 になっていたら
上げる。ただし **Pass を成立させるための引き下げは禁止**):

- **確認**: 失敗シナリオが実際に成立する → 修正対象
- **棄却**: シナリオが成立しない・spec の誤読 → 棄却理由を 1 文で記録(修正しない)
- **許容**: 指摘は事実だが、仕様上許される意図的な設計判断として修正しない。P2 以下のみ選べる
  (**P1 の許容は不可**)。理由を記録し、最終報告に必ず記載する
- **仕様未定義**: spec に答えがなく、永続データの意味・状態遷移・採点・SRS・認可境界など
  「意味が変わる」選択が必要 → このリポジトリの成果物なら停止条件に該当するので、ループを
  中断し `TODO(owner)` を追記してユーザーに報告する(勝手に仕様を決めない)。リポジトリ外の
  成果物なら TODO 追記は行わず、争点を整理してユーザーに確認する

### 4. 修正

確認された P1・P2 を修正する。P3 は文脈上ついでに直せるものだけ直してよい。

- 修正は指摘に対する最小限に留め、スコープを広げない
- テストを持つリポジトリでは、修正後に関連する検証コマンドを実行して壊していないことを
  確認する(このリポジトリなら `npm test` / `npm run typecheck` / `npm run lint` /
  `npm run validate-bank` / `npm run db:check` など、対象に関係するもの)

### 5. Pass 判定と再レビュー

Pass 判定は、手順 3 のトリアージで見直した**後**の severity に基づいて行う(レビュアーの
出力値そのままではない)。

**Pass 成立の条件**: あるラウンドのレビューで、トリアージ後の**新規 P1・P2 指摘が 1 件も
出なかった**こと。すなわち、全レビュアーが PASS を返したか、出た指摘が「P3」または
「既決事項の再提出」のみだったラウンドで Pass が成立する。

**P1・P2 について修正・棄却・許容を行ったラウンド自身は、決して Pass にならない。** 修正が
正しかったか、棄却・許容の判断が誤っていなかったかは、次ラウンドの独立したレビュアーによる
再レビューでしか確かめられないため。**P3 はこの限りではない**: P3 のみが出たラウンドは、
その P3 を棄却しても、あるいはついでに修正しても Pass が成立する(「軽微」という定義ゆえの
意図的な割り切り。ただし Pass ラウンドで行う P3 修正は誰にも再レビューされないため、typo
修正程度の機械的なものに限る。迷ったら修正して次ラウンドを回す)。

- トリアージ後の新規 P1・P2 指摘が 1 件でも出たら(全件を棄却・許容した場合でも)、手順 2 に
  戻り、**新しいサブエージェント**で次ラウンドを実行する
- **P1 棄却の特則**: 複数のレビュアーが独立に同じ P1 を検出した場合——同一ラウンド内で
  複数レビュアーの指摘が一致した場合も、過去のラウンドで棄却した P1 が後のラウンドで
  再提出された場合(直前のラウンドに限らない)も含む——それは強いシグナルなので、
  **棄却したいなら既決化せずループを中断し**、争点と自分の見解をユーザーに提示して判断を仰ぐ
- 過去のラウンドで棄却・許容した P2・P3 が再提出された場合は判断を再検討し、2 度目も同じ
  判断なら「既決」として扱ってよい(既決は、その判断を下したラウンド以降の Pass 判定で
  新規指摘に数えない)。既決とした指摘は最終報告に必ず記載し、ユーザーが判断を事後検証
  できるようにする
- Pass が成立したら、その時点の成果物を最終成果物として確定し、手順 6 の報告へ進む

### 収束ガード(無限ループ防止)

- **最大 5 ラウンド**。到達したら Pass 未成立のままループを打ち切り、未解決の指摘一覧と
  各ラウンドの経緯をユーザーに報告して判断を仰ぐ
- 同一箇所への修正が振動している(直す→戻すを繰り返す)ことに気づいたら、ラウンド上限を
  待たず打ち切って報告する。振動は大抵、仕様が曖昧であることのサインなので、争点を
  仕様の問いとして提示する

### 6. 最終報告

以下の形式で報告する。見出しは結果に応じて **「Pass(N ラウンド)」** または
**「打ち切り(N ラウンド・Pass 未成立)」** とし、打ち切りを Pass と紛らわしく書かない:

```markdown
## 🔁 敵対的レビューループ結果: Pass(N ラウンド)
<!-- 打ち切り時: ## 🔁 敵対的レビューループ結果: 打ち切り(N ラウンド・Pass 未成立) -->

### 対象
<レビュー対象の要約>

### ラウンド履歴
| ラウンド | 指摘 (P1/P2/P3) | 確認 | 棄却 | 許容 | 主な修正 |
|---|---|---|---|---|---|
| 1 | 2/1/3 | 3 | 3 | 0 | <要約> |
| 2 | 0/0/1 | 0 | 0 | 0 | なし(Pass) |

### 最終成果物
<Pass した時点のファイル一覧。この状態を最終成果物として確定>
<!-- 打ち切り時: 未解決の指摘一覧と、ユーザーに判断してほしい争点 -->

### 棄却・許容・既決とした指摘(あれば)
- <指摘の要約> — 棄却/許容/既決の理由
```

### コミットとの関係

このスキルの Pass は、**このリポジトリの実装契約(README「常時遵守」6)が求める
コミット前の Codex 第二者レビュー(`/codex:review`)を代替しない**。両者は独立した品質ゲート。

- 既定では、Pass 後のコミットは行わず、ユーザーの指示(または `smart-commit` 等の別スキル)に
  委ねる
- ユーザーが最初から「レビューして通ったらコミットして」と指示している場合はコミットまで
  進んでよいが、その場合も実装契約が要求するコミット前レビューを先に実施する
  (実施できない環境なら、未実施であることを報告に明記する)

## 注意事項

- レビュアーに「これは正しいはずだが念のため見て」のような誘導を書かない。成果物と仕様だけを
  渡し、判断はレビュアーに委ねる
- ラウンドをまたいでレビュアーを使い回さない。独立性がこのスキルの根幹
- Pass を急いで severity を恣意的に下げない・棄却/許容を乱用しない。P1 を P3 に付け替えたり
  安易に許容したりして Pass させるのは、このスキルの目的そのものの放棄
- レビュー対象外のファイルに手を広げない。ループ中に見つけた対象外の問題は最終報告に
  「別件」として記載するに留める
