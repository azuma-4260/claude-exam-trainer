# adversarial-review-loop スキル

## 設計思想

自分が作った成果物を自分で見直すと確証バイアスがかかる。そこで、成果物の作成に関与して
いない**独立したコンテキストのサブエージェント**に敵対的な立場でレビューさせる。

ただし、敵対的レビューは**証明器ではなく、確率的な欠陥発見メカニズム**である。レビュアーは
「問題を見つけること」が仕事なので、品質が十分でも低確度の指摘や改善案を生成し続ける。
したがって「指摘がゼロになるまで回す」は終了条件として成立しない。このスキルの終了条件は
「レビューで何も出なくなったか」ではなく、**「証拠に裏付けられた Blocking 欠陥が残って
いないか」**である。

このために 3 つの役割を分離する:

| 役割 | 担当 | 目的関数 |
|---|---|---|
| Coder(修正) | 本体 | 確定した指摘を直す |
| Reviewer(欠陥発見) | サブエージェント(毎ラウンド新規) | 欠陥を見つける。**停止権限を持たない** |
| Arbiter(終了判定) | 本体(レビューと別の帽子) | 「残った指摘は、追加変更の回帰リスクとコストを正当化するほど重大か」だけを判定 |

**重要: このスキルの呼び出し自体がループ実行の承認。** ラウンドごとにユーザーへ確認せず、
ACCEPT または ESCALATE に達するまで自律的に回すこと。

サブエージェントの起動には、この環境でサブエージェント委譲に使うツール(環境により
`Agent` または `Task` という名前)を使う。どちらも使えない場合はこのスキルの根幹が
成立しないため、自分でレビューを代替せず、その旨を報告して中止する。

## severity と証拠要件

| severity | 定義 | 終了への影響 |
|---|---|---|
| BLOCKER | correctness / security / データ破壊・喪失 / 要件・仕様違反 | ゼロになるまで ACCEPT 不可 |
| MAJOR | 実害のある堅牢性・保守性・性能の問題 | 確認されたものは第 1 ラウンドで修正するが、ACCEPT を妨げない |
| MINOR | スタイル・好み・将来の改善・リファクタリング機会 | 修正せず backlog へ記載して終了 |

**BLOCKER には証拠が必須。** 次のいずれかを提示できないものは BLOCKER として扱わない
(MAJOR 以下へ降格し、降格理由を記録する):

- 失敗するテスト(または失敗する具体的な入力・手順)
- 要件・仕様との明確な矛盾(該当箇所の引用)
- 静的解析・コンパイル・実行時エラー
- 具体的な反例

「気になる」「怪しい」は停止を妨げられない。各指摘には confidence(0.0–1.0)を付けさせる。
confidence は Arbiter がどの指摘から検証するかの優先度の目安であり、**BLOCKER かどうかを
決めるのは証拠の検証結果だけ**——Arbiter の検証で証拠が実際に成立した指摘は、confidence の
値にかかわらず BLOCKER として扱う(自己申告の数値ラベルを検証済みの証拠より優先しない)。

## 処理手順

### 0. 準備(ループ開始前に 1 度)

1. **対象の確定**: 通常は未コミット差分と新規作成ファイル(untracked は `git diff` に
   出ないため `git status` で列挙する)。ユーザー指定があればそれに従う。対象を確定
   できない場合(差分も新規ファイルもない等)は、推測で広げずユーザーに確認する。
2. **要件の確定**: このリポジトリでは `specs/` が唯一の仕様ソース。対象に関係する spec と
   `AGENTS.md` の禁止事項を特定する。リポジトリ外の成果物や spec の対象外(スキル定義等)は、
   ユーザー要求・会話中の要件・AGENTS.md の規約が要件に相当する。
3. **決定的検証の特定**: テスト・lint・typecheck 等、機械的に合否が出る検証手段を列挙する
   (このリポジトリなら `npm test` / `npm run typecheck` / `npm run lint` /
   `npm run validate-bank` / `npm run db:check` のうち対象に関係するもの)。
4. **スナップショット**: `git status` に現れる未コミット変更・untracked ファイルの一式
   (対象外含む)をスクラッチ領域へコピーし、`git diff`(staged があれば `--cached` も)を
   保存する。**各ラウンド開始時にも取り直す**。これが best-so-far の候補と、レビュアー
   誤操作時の復元元を兼ねる。git 管理外の成果物ではファイルコピーに読み替える。

### 1. ラウンドの実行(最大 3 ラウンド)

各ラウンドは次の順で進める。

**(a) 決定的検証** — テスト等を実行する。落ちていたらレビューより先に修正する
(機械が検出できる欠陥にレビュアーのコンテキストを使わない)。

**(b) レビュー** — サブエージェントを起動する。毎ラウンド**新規**に起動し、前ラウンドの
レビュー内容は渡さない(前任者の結論への anchoring を防ぐ)。ただし第 2 ラウンド以降の
検証契約の遂行に必要な範囲として、**検証対象の指摘の要旨(場所と主張)と修正の差分**だけは
渡してよい。前レビュアーの推論・証拠・confidence・結論は渡さない。可能ならツールを読み取り系に
制限し、diff は本体が事前取得してプロンプトに同梱する。既定は観点の異なる 2 体並列
(A: 仕様適合・正確性 / B: 堅牢性・エッジケース。ドキュメント対象なら「矛盾・曖昧さ・
実行不能な指示」に読み替える)。小さな成果物は 1 体に両観点を兼務させてよい。

**ラウンドが進むごとにレビュー範囲を単調に縮小する**(毎回全面レビューをすると、新しい
指摘が無限に生成されループが終わらないため):

| ラウンド | レビュー契約 |
|---|---|
| 1 | 全面的な敵対的レビュー(全観点・全 severity) |
| 2 | 前ラウンドの修正が正しいかの検証 + **新規は BLOCKER のみ**受理 |
| 3 | 未解決 BLOCKER と前ラウンド修正の検証 + **新規は BLOCKER のみ**受理 |

縮小されるのは MAJOR・MINOR の受理である。**BLOCKER はどのラウンドでも Arbiter 検証の
対象**であり、証拠が成立すれば ACCEPT を阻む(証拠付き BLOCKER を「契約外」を理由に
backlog へ落として ACCEPT してはならない)。契約外の新規指摘(第 2 ラウンド以降の新規
MAJOR・MINOR)は backlog に記録するだけで、修正もラウンド継続の理由にもしない。

レビュアーへのプロンプトには以下を必ず含める:

```
あなたは敵対的レビュアーです。成果物の欠陥を見つけることが仕事です。欠陥の見逃しも、
存在しない欠陥の捏造も失敗です。あなたに終了判定の権限はありません。

あなたは読み取り専用です。一切のファイルを変更・作成・削除せず、報告だけを返して
ください。

## レビュー対象
<対象ファイル一覧。差分レビューなら diff 本文を同梱>

## 要件(必ず読むこと)
<関連 spec のパス、AGENTS.md の禁止事項、ユーザー要求の要約>

## 今ラウンドのレビュー契約
<上の表のとおり。第 2 ラウンド以降は範囲の限定を明記>

## 担当観点
<観点 A または B、または両方>

## severity の基準と証拠要件
- BLOCKER: correctness / security / データ破壊 / 要件違反。
  「失敗するテストまたは失敗する具体的な入力・手順」「要件との明確な矛盾(引用)」
  「静的解析・コンパイル・実行時エラー」「具体的な反例」のいずれかを必ず添えること。
  添えられない場合は MAJOR 以下として報告すること。
- MAJOR: 実害のある堅牢性・保守性・性能の問題
- MINOR: スタイル・好み・将来の改善

## 出力形式(最終メッセージにこの形式だけを返す)
最初に「読了: <実際に読んだファイル・資料の一覧>」を 1 行で記載。
その後、指摘ごとに:
- severity: BLOCKER / MAJOR / MINOR
- confidence: 0.0-1.0
- 場所: ファイルパス:行番号
- 主張: 何が問題か(1〜2 文)
- 証拠: 上記の証拠要件を満たすもの(BLOCKER は必須、他も可能な限り)
- 違反する要件: 該当があれば spec・要求の該当箇所
- 修正案: 1 行程度

指摘が 1 件もない場合のみ、最終行に「指摘なし」と書いてください。
```

レビュアー返却直後、**ラウンド開始時スナップショットとの内容比較**で作業ツリーが改変されて
いないか確認する。照合は**スクラッチ領域へコピーした一式との内容照合(untracked 含む)**を
主とし、`git diff` の再取得・照合を併用する(`git status` の前後比較や `git diff` 照合
だけでは、untracked ファイルへの内容改変を検出できない)。改変されていたら、現在の状態を別途退避したうえで当該ラウンド開始時点の
スナップショットへ巻き戻し(ユーザーの並行編集だった可能性に備え、退避したものは最終報告
まで保持)、そのラウンドのレビューは作り直す。出力が空・エラーのレビュアーは 1 回だけ
再起動する。

**(c) Arbiter 検証(evidence validation)** — 指摘を鵜呑みにせず、本体がコードと要件を
読み直して各指摘の証拠が実際に成立するかを確認する:

- **成立**: 修正対象として確定
- **不成立**: 棄却。理由を 1 文で記録(捏造・誤読への追従は正しいコードを壊す)
- **証拠不備の BLOCKER**: MAJOR 以下へ降格し、降格理由を記録
- **仕様未定義**: 永続データの意味・状態遷移・採点・SRS・認可境界など「意味が変わる」
  選択が必要な争点は、このリポジトリの停止条件に該当。ループを打ち切り、`TODO(owner)` を
  追記して ESCALATE(リポジトリ外の成果物なら TODO は付けず争点を整理して ESCALATE)

Pass させるための恣意的な降格・棄却はこのスキルの目的の放棄である。棄却・降格は全件、
理由付きで最終報告に記載し、ユーザーが事後検証できるようにする。

**(d) 修正** — 確定した BLOCKER(第 1 ラウンドでは確定した MAJOR も)を修正する。
ただし、修正による回帰リスクが利益を上回ると Arbiter が判断した MAJOR は、理由付きで
backlog へ回してよい(BLOCKER にこの選択肢はない)。修正は指摘への最小限に留め、
スコープを広げない。修正後に決定的検証を再実行する。

**(e) 進捗の記録** — ラウンドごとに記録する: 検証済み BLOCKER 数 / MAJOR 数 /
決定的検証の結果 / 新規・解決・再燃した指摘。この記録が終了判定と best-so-far 選定の
根拠になる。

### 2. 終了判定(Arbiter が行う。結果は ACCEPT か ESCALATE の二値のみ)

**ACCEPT の条件(すべて満たすこと)**:

1. 決定的検証がグリーン(対象に該当する検証が 1 つもない場合——純粋なドキュメント等——は
   空成立とし、その旨を最終報告に記載する)
2. 検証済み BLOCKER がゼロ(未解決の BLOCKER が残っていない)
3. **最終ゲート**: 最後に修正を加えた後の状態を、**フレッシュな最終レビュアー**が確認して
   いること。最終レビュアーには過去の議論を一切渡さず、「要件 + 最終状態(diff)+
   決定的検証の結果」だけを渡し、**最終状態全体に対する evidence-backed BLOCKER の有無
   だけ**を見させる(ラウンドとは別枠の軽量ゲート)。直前のレビューが修正なしで終わり、
   **かつその契約が最終状態全体への新規 BLOCKER 探索を含んでいた場合に限り**、そのレビューが
   最終ゲートを兼ねる(未解決 BLOCKER の検証だけを行ったレビューはゲートを兼ねられない)。
   ゲートで証拠付き BLOCKER が出たら修正に戻り、**その修正はラウンドを 1 消費する**
   (上限に達していれば ESCALATE)。ゲート起因で修正に入る場合も、修正前にスナップ
   ショットを取り直す。ゲートレビュアーの返却直後にも手順 (b) と同じ改変検知を行う
   (確定直前の最後の 1 回だけを無検査にしない)。ゲートが別枠で増殖することはなく、
   全体の停止はラウンド上限が保証する

**ESCALATE の条件(いずれかに該当した時点で即)**:

- 3 ラウンドで ACCEPT に至らない
- ラウンド終了時の未解決 BLOCKER 数が、前ラウンド終了時より減っていない(無進捗。
  この比較は前ラウンド終了時に未解決 BLOCKER が 1 件以上あった場合にのみ行う——
  0 件のまま推移するのは無進捗ではなく ACCEPT へ向かう正常な状態)
- 一度修正した指摘が再び成立する(再燃 1 回で発動。修正 → 差し戻しの振動は仕様が
  曖昧なサイン)
- 独立した複数のレビュアーが同一の BLOCKER を挙げているのに、本体はそれを棄却したい
  (自分の棄却判断より独立した複数検出のシグナルを優先し、ユーザーに委ねる)
- 仕様未定義の争点に当たった(前述)

**ESCALATE は「未解決のまま合格扱い」ではない。** 争点・証拠・自分の見解・推奨する判断を
添えてユーザーに委ねる終端である。逆に、レビュアーが MINOR や低確度の指摘を出し続ける
ことは ACCEPT を妨げない——それらは backlog に落として終了する。

### 3. best-so-far

品質はラウンドごとに単調増加するとは限らない(修正が改悪になることがある)。各ラウンドの
スナップショットと進捗記録を候補として保持し、**ESCALATE 時は最終状態ではなく、記録上
最良の候補**(未解決 BLOCKER が最少で、決定的検証がグリーンなもの)を特定して報告する。
記録とスナップショットの対応に注意: ラウンド N の修正後の状態に対応するのは、ラウンド
N+1 開始時のスナップショット(最終ラウンドでは現在の作業ツリー)である。
最終状態が best でない場合は、どのスナップショットが best かと差分の要約を示し、巻き戻す
かどうかはユーザーの判断に委ねる(勝手に巻き戻さない)。ACCEPT 時は最終状態がそのまま
確定成果物となる。

### 4. 最終報告

```markdown
## 🔁 敵対的レビューループ結果: ACCEPT(N ラウンド)
<!-- または: ESCALATE(N ラウンド・要ユーザー判断) -->

### 対象
<レビュー対象の要約>

### ラウンド履歴
| ラウンド | BLOCKER(検証済/棄却・降格) | MAJOR | MINOR | 決定的検証 | 主な修正 |
|---|---|---|---|---|---|
| 1 | 2 / 1 | 3 | 4 | green | <要約> |
| 2 | 0 / 0 | -(契約外) | - | green | 修正の検証のみ |
| 最終ゲート | 0 / 0 | - | - | green | なし |

### 確定成果物(ACCEPT 時)/ 争点と best 候補(ESCALATE 時)
<ACCEPT: ファイル一覧。ESCALATE: 争点・証拠・自分の見解・推奨判断・best スナップショット>

### backlog(修正しなかった指摘)
- <MINOR / 契約外指摘 / 未修正 MAJOR の一覧。ユーザーが後で拾えるように>

### 棄却・降格した指摘
- <指摘の要約> — 棄却/降格の理由(証拠が成立しない・証拠不備 等)
```

N は着手したラウンド数(途中で終了した当該ラウンドも含む)。

### コミットとの関係

このスキルの ACCEPT は、このリポジトリの実装契約(README「常時遵守」6)が求める
コミット前の Codex 第二者レビュー(`/codex:review`)を**代替しない**。既定ではコミットは
行わず、ユーザーの指示(または `smart-commit` 等)に委ねる。「通ったらコミットして」と
指示されている場合も、実装契約のコミット前レビューを先に実施する(実施できない環境なら
コミットせずその旨を報告して指示を待つ)。

## 注意事項

- レビュアーに「これは正しいはずだが念のため」のような誘導を書かない
- ラウンドをまたいでレビュアーを使い回さない。独立性がこのスキルの根幹
- レビュー対象外のファイルに手を広げない。ループ中に見つけた対象外の問題は backlog に
  「別件」として記載するに留める
- 終了判定をレビュアーに委ねない。「もう十分か」を決めるのは Arbiter(本体)であり、
  判定基準は常に「証拠付き BLOCKER の有無」と「追加変更の期待利益がリスクを上回るか」
